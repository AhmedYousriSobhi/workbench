# Testing a monitoring client against workbench

workbench simulates a real cluster so that a general-purpose HPC and AI-infrastructure client, one that lets its user
define any cluster and handles every connection type and HPC feature, can be tested without real hardware. The client
connects to workbench exactly as it would to a production site (SSH to a login node, Slurm commands, Grafana GPU
metrics, Jira search, Redfish BMCs); the user then writes scenarios (faults, outages, workloads) and watches how the
client reacts. This page is the checklist for a fresh session: bring the stack up, point the client at it, run a
scenario, and know what is real and what is not. The client's own repository is separate and is never named or copied
here. Because the client is general, never fit workbench to one client's quirks: make the simulated service behave
like the real one.

## What a client needs, and where it is

Every part has a fixed private address (`10.141.x.x`, standard ports; [ADR 0018](../adr/0018-fixed-addressing-plan.md)), reachable from this machine because Linux routes the Docker network; the ports published on `127.0.0.1` stay as the fallback. Secrets are generated by `benchctl up` into `compose/generated/secrets/` (gitignored;
never print or commit them).

## Bring it up

```bash
./scripts/benchctl up --profile min     # refused when host memory is low (governor GV-9): free RAM and rerun
./scripts/benchctl status
./scripts/benchctl down                 # when done; always stop what you started
```

`up` prints the `ssh:` line and the token file names. The cluster has partitions `cpu` (4 nodes) and `gpu` (2 nodes,
8 `h200` GPUs each); users `alice` and `bob`.

## Point the client at it

- **Execution target:** set a node such as `cn001` as the scheduler's execution target (the client runs `ssh <node> <command>` from the login node); no keys to set up, the login node already trusts the nodes.
- **SSH:** host `10.141.255.254`, port `22` (fallback `127.0.0.1` / `2222`), user `alice`. Many clients only read private keys under `~/.ssh`. Run
  `./scripts/benchctl ssh-key install`: it copies the generated key to `~/.ssh/workbench_ed25519` (mode 600) and prints the
  path to give the client. Run `./scripts/benchctl ssh-key remove` when done. Alternatively load the key into a throwaway
  `ssh-agent` (`eval "$(ssh-agent -s)"; ssh-add compose/generated/secrets/ssh/id_ed25519`) and use agent authentication.
- **Host key:** the first connection needs the client's trust-on-first-use confirmation. `up` keeps the same host key
  across restarts, so the pin stays valid.
- **Slurm:** the client's refresh runs fixed `squeue`/`sinfo` commands; submit work as `alice` with
  `sbatch --wrap="sleep 300" -p cpu` (add `-p gpu --gres=gpu:2` for GPUs) so there is something to show.
- **Drain a node** for the node-issues view: `docker exec <slurmctld container> scontrol update nodename=cn004
  state=drain reason="test"`, and `state=resume` afterwards.
- **GPU panel:** set the datasource uid to `prometheus`, the host label to `Hostname`, and the Viewer token. Per-job
  GPU usage appears only while the SSH user has a running job, and the GPUs of that job read busy (the others idle).
- **Jira:** base URL `http://10.141.255.11:8080` (a client that refuses plain HTTP for a non-local host: use the fallback `http://127.0.0.1:8080`). `POST /sim/tickets` and the ticket scenarios ([tickets guide](jira-tickets.md)) file and move tickets; **a team changes tickets in the background** (`benchctl set jira-activity off` stops it, [guide](jira-tickets.md)) and **a node fault files one ticket by itself** (project OPS, reporter `ops-bot`, labels `node-<name>`, `fault-<kind>`, `auto`): Power off, GPU error (XID), overheat and fan failure each open one per node and kind (a repeat comments), Power on or Clear faults comments and resolves it, from the page, `benchctl set node` and scenarios alike; `POST /sim/failure` injects 401,
  429, 503 or slow responses.

## Stress test: everything at once while the client runs

`benchctl scenario run client-stress` (5 minutes, [scenarios/client-stress.yaml](../../scenarios/client-stress.yaml)) floods five nodes with jobs, raises GPU XID errors and fan failures, heats a GPU node, powers off and drains `cn004`, files 12 tickets, then makes the Jira mock answer 429, slow and 503 before clearing everything. With the client connected to the real Jira (`jira-real`), run `client-stress-real` instead: same nodes, GPUs, heat and jobs, but Jira's own rate limit (429, about 75 to 180 s), a CAPTCHA lock for one user (use a personal access token for the client's own account, or it is locked out too) and a 30 s hang. It files its 12 tickets on the real Jira (only tickets made in the last 10 minutes are counted, so a repeat run does not add up). Run it with the client open and measure the client at the same time (use a `--match` that names only the client's own processes, such as its install path; a loose word such as `name` matches unrelated programs. The tool prints `matched: <program> xN (MB)` before it samples and warns when more than 4 different programs match; read that line before `--save`):

```bash
./scripts/benchctl scenario run client-stress &
./scripts/benchctl measure app --match NAME --duration 330 --save
```

**Running it with the real window, step by step (what was done once):**

1. Bring the workbench up with the real Jira (`benchctl start --with jira-real`, then `benchctl setup jira-real` once; `benchctl status` shows the licence end).
2. `benchctl export profile -o profile.json`, then `benchctl ssh-key install` (the client only accepts a key under `~/.ssh`; run `benchctl ssh-key remove` at the end).
3. Start the client in its dev mode with a throwaway config directory (`XDG_CONFIG_HOME=<empty dir>`) and `--remote-debugging-port=9222`. A fresh config asks for a local account (any name, no password), then offers to claim the existing profile (choose it, confirm, Continue).
4. Create the cluster through the client's own API from the profile file: the entry for the login node that takes a key, the key at `~/.ssh/workbench_ed25519`, the Grafana viewer token from `compose/generated/secrets/grafana_viewer_token`, and for the real Jira `http://127.0.0.1:8083` with `PAT_ALICE` from `compose/generated/secrets/jira-real.env`. Read the secrets from the files inside the script; never print them.
5. In the client, trust the host key and Connect; check SSH, Slurm, Grafana and the Jira section are green.
6. Measure idle (`measure app --duration 40`), then run the scenario, the measurement and a loop that opens every view (Grafana, Slurm with its Jobs, Nodes, Partitions and GPUs tabs, Storage, Tickets and docs, Notes) together.
7. Stop the client, remove the throwaway config and the installed key.

Measured this way: 469 MB idle; with every view opened and the scenario running, 664 MB peak, 555 MB typical. A first attempt whose clicks missed (the client only polled) peaked at 539 MB, which is why the views must be opened.

`client-stress` hits `jira-mock` (8080) and files its tickets there; `client-stress-real` hits `jira-real`. Measured once (a desktop Electron client, one cluster, a terminal, the real Jira, every view opened in turn): 469 MB idle, 664 MB peak and 555 MB typical during the scenario, 8 processes; the machine reserve was set to 800 MB. One session, one cluster: it is a floor for several clusters or terminals, not a limit.

## Slurm: what is real and what is not

Slurm is the real software (ADR 0025), so a client sees real command output and real state changes. Real: `squeue`, `sinfo`,
`sacct`, `scontrol` text and flags, node states (`down*`, `mixed`, `drain`), pending reasons (`ReqNodeNotAvail`), `slurmrestd`
JWT auth, and a frozen node going `down*` by itself after about 30 s. Simulated: GPUs (count-based GRES), jobs (`sleep`),
the node health checks' inputs and accounting storage unless the `accounting` part is on. **Not exercised:** cgroup limits,
real GPU binding, resource contention, and `gres/gpu` in `AllocTRES` without `slurmdbd`. Do not report one of these as a
client defect.

## Verifying without a GUI

A headless check is faster than driving a window: connect with any SSH library to `127.0.0.1:2222`, run the client's
fixed Slurm command and parse it with the client's own parser. `tests/real/test_login_real.py`,
`tests/real/test_gpu_grafana_real.py`, `tests/real/test_bmc_tls_real.py` and `tests/real/test_mocks_real.py` assert
the same wire behaviour against the live stack (`WORKBENCH_REAL=1 pytest tests/real/<file> -q`).

For the real window, run the client in its dev mode with a throwaway config directory and a remote-debugging port,
create a synthetic profile through its own API, then read screenshots and page text over that port. Use synthetic
data only, stop every process you start, and never commit screenshots that show real data.

Fastest start: import the whole cluster from a file with `benchctl export profile` ([export-profile.md](export-profile.md)). Setting up each part of the client one at a time (SSH, Slurm, Grafana, storage, Jira, BCM, BMC): [client-setup-by-component.md](client-setup-by-component.md).

SSH connection handling (hung, down, changed host key, session limit), step by step with screenshots: [ssh-connection-testing.md](ssh-connection-testing.md).

## Write a scenario and watch the client

A scenario is a YAML file in `scenarios/` (see [scenarios and faults](../manual/06-scenarios.md)); steps run at
offsets and can target `bmc-farm`, `bcm-mock`, `gpu-exporter`, `jira`, `slurm` and `ssh` (login-node host key, down, hung, session limit; Kubernetes and the ticket bot are
not built; their steps are skipped).

```yaml
name: gpu-node-overheats
description: A GPU node fans out and overheats, then Slurm drains it and it recovers
steps:
  - {at: 0s,  target: bmc-farm, do: {nodes: [gpu002], fan_fail: 3}}
  - {at: 5s,  target: bmc-farm, do: {nodes: [gpu002], ramp: {to: 92, over: 30s}}}
  - {at: 20s, target: slurm,    do: {drain: [gpu002], reason: "overheating"}}
  - {at: 60s, target: bmc-farm, do: {nodes: [gpu002], clear: true}}
  - {at: 60s, target: slurm,    do: {resume: [gpu002]}}
```

```bash
./scripts/benchctl scenario list
./scripts/benchctl scenario run gpu-node-overheats --dry-run   # validates node names and targets
./scripts/benchctl scenario run gpu-node-overheats --speed 4   # 4x faster
```

Run it while the client is connected and compare what the client shows (node state, reasons, alerts, GPU temperature
and XID metrics, BMC events, Jira failures) against what the scenario did. New fault kinds belong in the scenario
engine's targets, not in ad hoc `docker exec` commands.

## Things that look like bugs but are not

- Slurm GPU counts in a client come from node state (a node with a running job reads `mixed`), not from GRES
  allocation; the simulator cannot report `gres/gpu` in `AllocTRES` without `slurmdbd` (issue #129).
- A client's node inventory may refresh more slowly than its jobs list, so a node can look idle for a few seconds
  after a job starts.
- `sinfo` folds names (`cn[001-004]`); assert on the fold, not on single names.

## Known gaps

Kubernetes has no real kubelet (no pod logs, no metrics-server) and is not reachable through Teleport; Teleport is SSH access only (no dynamic labels, session recording or sharing); the fake `cmsh` console is a read-only subset.
The full list is the roadmap, issue #69.

## Node health check (what drains a node)

Every `slurmd` runs `/usr/local/sbin/nhc` (source `images/node-base/nhc`, a small stand-in for LBNL NHC) three ways: every 30 s
(`HealthCheckProgram`), before each job starts on the node (`Prolog=nhc-prolog`) and after it ends (`Epilog=nhc-epilog`). It reads
the exporter farm and **drains the node** with a reason starting `NHC:` when:

| Check | Fault to inject | Reason in `sinfo -R` |
|---|---|---|
| GPU missing (fewer series than the GRES) | none yet (a fault action is not modelled) | `NHC: GPU count 7 of 8` |
| GPU XID error | **GPU error (XID 79)** | `NHC: GPU XID 79` |
| InfiniBand port down (one HCA per GPU, one port on a CPU node) | **InfiniBand port down** | `NHC: IB port down: mlx5_0` |
| NIC link flapping (`node_network_carrier_changes_total` keeps rising) | **NIC flapping** | `NHC: NIC eth0 flapping (4 link changes)` |

The list of checks is not fixed: add your own, switch one off or reorder them from the command line, by editing files or in the page's **Health checks** sheet, with every change validated and live within 30 s ([NHC checks](nhc-checks.md)). The periodic run drains within about 30 s and resumes a drain it made itself once the fault is cleared (never one an operator
set). The **prolog** fails an unhealthy node, so Slurm requeues the job instead of running it there; the **epilog** drains a node
that a job left unhealthy, so the next job is not scheduled on it. A node that publishes nothing (powered off) and an unreachable
exporter are not drained. A cluster built before this needs `benchctl up` once: it rebuilds the node image (the prolog and epilog
scripts are in it) and restarts `slurmctld`. Without the rebuilt image a job start fails on a missing prolog and drains the node.

**Tickets for what Slurm does.** `slurmctld` also runs a watcher (`images/slurm-ctl/node_watch.py`) that polls `sinfo` every 10 s: a
node that turns DOWN or drained files a ticket (kind `slurm`, or a comment on the node's open ticket, so a Power off stays one
ticket), and one that comes back is resolved. That covers a node Slurm drained by the health check or by hand, and a node that went
down by not answering, which no page button or scenario step reports.

## A live queue

`benchctl load on` starts simulated users: `alice` and `bob` submit cpu jobs and 1 to 4 GPU jobs at random, so the Slurm panel has running and pending jobs and a node going down hits real work. `benchctl load off` stops it; `benchctl submit NODE` (or the node panel's Workload card) runs one job on a chosen node. A job pinned to a node that is down stays pending (*ReqNodeNotAvail*) until the node is back or you `scancel` it.

## Taking a node down so Slurm notices

**Power off** on the page (or `benchctl set node cn001 off`, which does the same) sets the BMC, BCM and GPU metrics and freezes the node's container: its `slurmd` stops answering and
`slurmctld` marks it `down*` (Not responding) by itself after about 30 s (a client then shows it on its next poll: 60 s with the Slurm section open and the window focused, 5 min otherwise), which is what a monitoring client sees on a real
