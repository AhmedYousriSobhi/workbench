# ADR 0042: On-demand message capture for one wire

Status: accepted (owner decision of 2026-11-11). Issue 505, epic 491; follows ADR 0041. SPEC W-18.

## Context
The Focused wire panel (ADR 0041) can say only what is documented about a node's wires: the always-on request counters mask a node name in a path
(`{id}`) to keep the metric count bounded, so one node's requests cannot be told from another's. The owner asked for the messages of **one** wire on demand,
without making the counters unbounded and without an always-on capture.

## Decision
- **Off by default, one wire, a bounded life.** A capture starts when the panel opens and ends when it closes, when the tab or page hides, when nobody has
  read it for 15 s, when the ladder reaches L2, or after 5 minutes. Only one runs at a time. It is started, read and stopped only through the governor
  (`capture-start`, `capture-read`, `capture-stop`, validated like every command): the page never touches Docker (W-3). It starts only at L0-L1, as a
  class P5 workload (about 5-10 MB while running, nothing after), and is audited (`capture start`, `capture stop: <why>`).
- **Nodes by IP address.** The capture maps a peer's address to a name through the addressing plan (ADR 0018); the counters' paths stay masked.
- **Slurm.** `benchctl get capture NODE` runs `tcpdump` (already in the node image) inside the node's container through `docker exec`, snaplen 256, filtered to
  ports 6817 and 6818, ended by `timeout` and a packet count. The pcap stream is decoded in Python (Ethernet, Linux cooked v1 and v2). A message starts where
  the previous one on that connection ends (its length prefix and the TCP sequence number say where). The header is `u32 length, u16 version, u16 flags,
  u16 msg_type, u32 body_length` (all network order; read from `src/common/slurm_protocol_pack.c` of the pinned release). The parser accepts exactly the pinned
  protocol version (`45 << 8` for 26.05), a type that release defines and a length that holds the body; anything else is **unknown**: direction, size and timing,
  never a guess. The type table (`benchctl/slurm_msgtypes.py`, 261 types) is generated by `scripts/gen_slurm_msgtypes.py` from that release's own
  `msg_type.h` (the tarball's SHA-256 is pinned in `images/node-base/Dockerfile`); regenerate it when the pin changes. Two of the header's `/* NNNN */`
  comments (5040, 5042) disagree with the enum arithmetic; the compiler uses the arithmetic, and so does the table. A response's time is the gap since the
  last request the other way on the same connection. The body is not read (a response's result code is not decoded in v1).
  Rejected: raising slurmd's log level (needs a restart and changes what is observed).
- **Kubernetes.** The audit log is enabled with a narrow policy (`AUDIT_POLICY` in `benchctl/k8s.py`): metadata only, for nodes, node status, pods, pod status,
  pod bindings and leases; every other request, secrets included, is not logged; no request or response body. It goes to the API server's stdout, which Docker
  bounds at 10 MB (`max-size 5m`, `max-file 2`), and the capture reads it with `docker logs --since`. It keeps events about the node: its lease (the heartbeat),
  its node object and the pods whose `spec.nodeName` is the node (the pod list is read as the read-only viewer and refreshed every 30 s). "Requests from the
  KWOK identity" is read as KWOK's requests about this node, which these are; all of KWOK's traffic for other nodes is not kept.
- **Data handling.** Messages live in the governor's ring (500) and the page's memory; they are not written to `compose/generated` or committed, and a new
  capture forgets the last. They would enter a test report only if the person exports one (not built in v1).
- **Not in v1:** more than one wire at once; always-on capture; decoding a message body.

## Consequences
- The audit log is on for the API server whenever the Kubernetes part runs, not only during a capture (a policy cannot be switched at runtime). It is narrow
  and bounded, and the only always-on cost is those lines in Docker's log file.
- A Slurm connection already open when the capture starts is joined mid-message: the next packet that parses resyncs it, and until then it can show as unknown.
- With TLS between the Slurm daemons (not used here) every header would be unknown; the panel would say so rather than guess.
- A real-host test (`tests/real/test_wire_capture_real.py`) exercises tcpdump in a real node and the real audit log.
