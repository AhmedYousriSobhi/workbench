# 0014. sshd on the nodes, and SSH faults as a scenario target

Status: accepted

## Context
A monitoring client with Slurm on another host runs `ssh <node> <command>` from the login node, using the login
user's own keys, and expects no prompt. It also verifies the login node before and while it is connected: a banner
probe (TCP, read `SSH-`, reply, close) that maps failures to refused, timeout, no route or not-SSH; a pinned host key
whose change must stop the connection; keepalives and reconnects. ADR 0011 gave only the login node an `sshd`, and the
only way to break it was stopping the container by hand.

## Decision
- **sshd on every compute and GPU node**, started by node-base's entrypoint only when compose sets
  `HPCSIM_NODE_SSHD` (nodes in a profile that has a `login`). Key login only, no root, same users, same
  `authorized_keys`, Slurm tools linked into `/usr/local/bin` for non-interactive sessions. No published port: nodes
  are reached through the login node (hop, ProxyJump, `srun`).
- **One host key shared by every node** (`ssh_node_host_ed25519_key`, generated by `simctl up` next to the login
  key). The login node trusts it for every node name in `/etc/ssh/ssh_known_hosts`, so a first hop does not prompt
  and an unknown host name is still refused.
- **The client key is also each simulated user's key on the login node** (`~/.ssh/id_ed25519`), authorised on the
  nodes. It is one closed lab key; real keys never enter the sim.
- **Scenario target `ssh`** (host CLI only, like `slurm`; skipped from the web page). Login actions: `down`/`up`
  (`docker stop`/`start`: refused), `hang`/`resume` (`docker pause`/`unpause`: the port accepts but no banner comes,
  a timeout; resume after N seconds is a slow banner), `reject_auth`/`accept_auth` (`DenyUsers *`: publickey refused),
  `limit`/`unlimit` (`MaxStartups`, `MaxSessions`: an extra connection is refused), `rotate_host_key`/
  `restore_host_key` (a new login host key, the original kept as `.orig`). Node action: `sshd: down|up` on `nodes`.
  Config faults go through `/etc/ssh/sshd_config.d/90-fault.conf` plus SIGHUP; the `Include` is first in the config
  because sshd uses the first value it reads.
- **`simctl up` builds node-base first and builds the controller image from `images/slurm-ctl`.** Each node-base build
  bakes a new munge key; the controller and login images are built `FROM` it, and the controller was never rebuilt by
  `up`, so a changed node-base left nodes and controller with different keys (Slurm "Protocol authentication error").

## Consequences
- `ssh cn001`, `ssh -J`/ProxyCommand through the login node and `srun --pty` work; the failure text on a hop to a
  stopped node is the real ssh error.
- Each node carries about 3-5 MB for `sshd` inside its 60 MB limit; the Phase 0 measurement stays the authority.
- Not built: a non-SSH service answering on the login port (a client's "not SSH" reason), extra SSH endpoints
  (issue 140), Teleport (issue 77).
