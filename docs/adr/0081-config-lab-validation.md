# ADR 0081: Config lab validation with the real tools

Status: accepted (owner decisions of 2026-11-15). Issue 552; epic 557. Builds on ADR 0049 and 0050.

## Decision

- **What is checked: the baseline, rendered.** `benchctl validate lab NAME` checks the imported configuration after the lab has made it its own (`compose/generated/lab/NAME/render/`: the downscaled nodes, lab-owned keys replaced by the workbench's, time-scaled keys divided by the dilation factor), not the raw import, which holds production hosts and paths the lab replaces. The result shows which keys the lab replaced. `--side candidate` prints one line naming issue 553 and exits 3 (not available: neither a pass nor a failure) until the candidate overlay exists.
- **Slurm.** A throwaway slurmctld from the controller image: `--network none` (it cannot meet the live slurmdbd or nodes), a fresh container filesystem (so an empty `StateSaveLocation`, never the live one), `--memory`, `--rm`, its own munge key made and its `munged` started inside, and no `workbench.class` label (the governor would freeze it). Pass when the log says it started or is running as primary within 20 s; fail on the first `fatal:` line, shown as is. `error:` lines do not fail (unresolvable node names, cgroup notices and an unreachable slurmdbd are expected in a container without a network); they are listed as warnings. `restart_required` is true when an applied key needs a slurmctld restart (`lab_slurm.restart_required`).
- **Accounting.** `sacctmgr` talks to slurmdbd, so a scratch database alone does not work: (1) leftover `lab_validate_*` databases are dropped, then `lab_validate_<id>` is created on the running MariaDB (the `slurm` user is granted CREATE, DROP, ALTER, INDEX, SELECT, INSERT, UPDATE, DELETE, LOCK TABLES and CREATE TEMPORARY TABLES, the privileges slurmdbd needs to build and use its tables, on `` `lab\_validate\_%`.* `` only: no GRANT OPTION, nothing global. In a grant's database pattern `_` and `%` are wildcards, so the underscores are escaped and a test proves the pattern does not match `slurm_acct_db`. The same statement is applied at every `benchctl up` as MariaDB's root, through `docker compose exec` with the password read inside the container from its environment (never printed or logged), because the init directory (`slurm/lab-grant.sql`) only runs when the database is first created; a GRANT is idempotent, so an existing stack needs no restart. `mariadb.env` therefore holds a generated `MARIADB_ROOT_PASSWORD` (kept across regenerations, mode 600, gitignored) instead of a random one nobody knows); (2) a throwaway slurmdbd on port 6899 points at it (a one-shot container on the stack network, the password from the existing env file, never on a command line); (3) the QOS of the export are created, `sacctmgr -i load` loads the dump, and `sacctmgr dump` reads it back for a diff (an account or user that did not load fails; a changed option is a warning); (4) the container is removed and the database dropped, also when a step raises. No rollback trick is used: the scratch database is simply dropped. When accounting is not running the result is `skipped` and says why; if the scratch database cannot be created the result is `failed` with the database's message.
- **Rules.** `promtool check rules` and `promtool test rules` run from the pinned Prometheus image with no network (`--entrypoint promtool`), over the imported rule files and `*.test.yml` files.
- **Kubernetes.** `kubectl apply --dry-run=server` of the imported policy manifests through the existing `kubectl_cmd` (official image, admin kubeconfig) when the Kubernetes part runs; an object in a namespace the same files create is reported as a warning (a dry run does not create the namespace); otherwise `skipped`.
- **Teleport.** The role structure check always runs: `kind: role`, a `version` this lab knows for Teleport 18 (v3 to v7; another `vN` is a warning because only a running Teleport can say), `spec.allow` or `spec.deny`, and known keys only, a close misspelling being an error with "did you mean". When the Teleport part runs, `tctl create` is also tried: `tctl create --help` (18.11.2, the local client; the pin is 18.11.8) has no `--dry-run`, so each role is created under a temporary `lab-validate-<id>-N` name, Teleport's verdict is read and the role is deleted at once. Results say "structure only" or "accepted by Teleport".
- **Also:** a secret scan over `baseline/` and `render/` (the import's rules) and the version check (a differing component is indicative, not a failure).
- **Result and summary.** Each result is `{tool, command, ok, messages[], restart_required}` plus `status` (passed, failed, skipped; `ok` is null when skipped), `warnings` and `note`, written to `validate.json`. The summary reads `passed`, `passed with N skipped` (never plain `passed` when something was skipped) or `failed (n of m)`; the CLI prints one line per tool.
- **Governor path.** The verb `lab-validate NAME [side]`: the name must match the lab pattern and exist on disk; one change at a time; L0 and L1 only (refused at L2 and up with one message); admitted as a P5 estimate of 250 MB (GV-9); audit-logged (GV-6); the governor runs `benchctl validate lab NAME --run-here` and the CLI waits for that change and prints `validate.json`. Every one-shot has its own timeout (90 s), so a run is bounded.

## Consequences

The generated accounting wiring changes: a root password in `mariadb.env` (a changed env file makes `up` recreate MariaDB once; its data directory is a tmpfs, so nothing is lost that `accounting-init` does not rebuild) and the grant at every `up`. Unit tests use an injectable executor and synthetic tool output (marked as such); the live test is `tests/real/test_lab_real.py` (`./scripts/verify.sh --unit lab --clean`), and real captures of each tool's output still have to be taken from it.

## Addendum: what the real tools printed (issue 778)

The first live run (`./scripts/verify.sh --unit lab --clean`) found that the synthetic tool outputs were wrong in six places. The fixtures under `tests/fixtures/lab/tool-output` are now captures (slurmctld, slurmdbd and sacctmgr 26.05.5, MariaDB 11.8), with the debug lines left out.

- **Isolation: `--network none` does not work for slurmctld, so the one-shot gets an `--internal` network of its own.** With no non-loopback interface slurmctld dies in `_open_ports` (`getaddrinfo((null):6817) failed`, then `fatal: Unable to listen`), also with `--add-host` and with `SlurmctldHost=name(127.0.0.1)`. The one-shot now joins `workbench-lab-validate-<id>`, created per run with `docker network create --internal` and removed in a `finally`: no gateway, no route out, and no workbench container is attached, so nothing resolves and every connect fails with "Network is unreachable". It is never `workbench_default`. `tests/real/test_lab_real.py` proves it against the live stack: a probe on the compose network reaches MariaDB (so the probe is not vacuous), the same probe on the throwaway network resolves no live name and connects to no live slurmdbd, MariaDB, slurmctld or login address nor to 1.1.1.1, the network has no attached container, and it is gone afterwards.
- **"Started" is `Running as primary controller`, not `started on cluster`.** slurmctld logs the second line first; the node, partition and plugin checks (and their `fatal:`) come a few milliseconds later, so the old pattern could stop the run before the fatal. A fatal after `started on cluster` is now a fixture and a test.
- **A partition `QOS=` is a `fatal:` without accounting** (`Partition gpu has an invalid qos (normal)`), so the one-shot drops that option from the partition lines and says so in a warning; `sacctmgr load` is where the QOS are checked.
- **The accounting one-shot** needed: `SlurmctldHost=` in its slurm.conf (sacctmgr: `No SlurmctldHost defined`); `GraceTime` in seconds (`show qos` prints `00:00:30`, `modify qos` rejects it); the `gres/gpu` TRES declared, which slurmdbd only learns from a slurmctld that registers with `AccountingStorageTRES=` (there is no `sacctmgr add tres`), so a slurmctld runs for a moment inside the one-shot against the scratch database, with one node, its own state and `AccountingStorageHost=localhost`; and the parser has to accept the `QOS - 'name':...` lines a real `sacctmgr dump` writes before the cluster (the import parser rejected them, so a real dump could not be imported either). The read-back sorts the account QOS list, so `normal,high` against `high,normal` is not a change.
- **The grant lacks `CREATE ROUTINE` and `ALTER ROUTINE`.** slurmdbd creates the stored procedure `get_lineage` in its database (`1370 alter routine command denied`). Until the owner decides on those privileges (and `EXECUTE`), the check reports `skipped: slurmdbd needs CREATE ROUTINE and ALTER ROUTINE ...` instead of `failed`, so it degrades honestly either way.
