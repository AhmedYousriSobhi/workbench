# ADR 0050: Config lab: A/B replay, comparison and verdict

Status: accepted (owner decisions of 2026-11-12). Issue 542; epic 557. Companion to ADR 0049.

## Decision

- **Shape-preserving downscale.** `lab.max_nodes` (default 24, max 64). Every (partition x node shape x topology leaf) group keeps at least one node; the rest is split in proportion to production counts. Partitions, QOS, accounts and topology levels are all kept. Multiple-slurmd mode stays out of v1 (issue 457).
- **Trace** is a `sacct` export (fields in the operator guide), sampled at the node ratio, stratified by account, QOS and partition. Each job is resubmitted with the mapped user, account, QOS, partition, TRES (typed GPUs included), nodes, time limit and relative submit time; its body is `sleep <scaled elapsed>; exit <code>` (timeouts sleep past the limit, OOM exits 137).
- **Names.** Production node names are kept as Slurm `NodeName` and hostname (compose service `lab-node-NNN`). Users map to `lab-u001...`, `--keep-users` keeps them.
- **Time dilation.** Default target 2 h per side (30 min to 6 h). Every time-based scheduling parameter (see `KEY_CLASS` time-scaled) is divided by the same factor in both runs and listed in the report.
- **Same faults, same seed.** An attached scenario runs with a fixed seed at the same dilated times in both runs.
- **Snapshot and restore.** Before run A save `StateSaveLocation` and a `mysqldump`; restore both before run B. Prometheus data carries a `lab_run` label instead of being restored.
- **Repeats.** One run per side by default; `--repeat N` (1 to 10, the CLI's range; corrected 2026-11-20, issue 554: it said at most 5) reports median and range (see the repeat-loop addendum for what is built); single runs are labelled.
- **Concurrency cap** `lab.max_running_jobs` (default 50). If the sampled trace exceeds it the import proposes fewer lab nodes rather than throttling submissions, so both runs see the same load.
- **Pressure.** Replay and validation one-shots are class P5 and admitted only if the estimate (250 MB) fits (GV-9). L2 pauses the replay clock (pauses are recorded; over 5 % of run length marks the run not comparable); L3 stops it as "aborted under memory pressure".
- **Verdict** (thresholds in `sim.yaml lab.verdict`, printed in every report): any hard failure (validation error, lost job, an alert that fired in A and not in B, still-pending up more than 20 %, median wait up more than 20 % in a partition with enough samples) is "Do not ship"; a new cost or a 5 to 20 % regression is "Ship with changes"; at least one improvement over 5 % and nothing worse is "Ship"; everything within 5 % is "No effect". A minimum sample size per partition keeps small partitions from causing false failures.
- **Suggestions** are rule-based from a small catalogue (preemptions with requeue, QOS limit dominating pending, idle-but-free GPUs, alert flapping, fairshare spread), never generated; "apply suggestion and rerun" edits the candidate overlay and starts a new A/B.
- **Report:** `report.md` and `report.json` under `compose/generated/lab/NAME/reports/RUN/`; `benchctl export lab-report NAME RUN --anonymize` (issue 614) maps production node names to lab names.

## Consequences

Policy behaviour (priority, fairshare, QOS, preemption, topology placement, Kubernetes admission and quotas, alert rule timing, Slurm state compatibility) is decided by the real software. Job runtimes, GPU and network contention, hardware timing, pod runtime and slurmctld load at production scale are approximate and labelled so in every report. A ratio above 100x marks results indicative.

## Addendum (issue 551, downscale, mapping, time scaling)

- Group key is the tuple of a node's partitions, its shape and its topology leaf (a node in two partitions is one group, so it covers both). A shape is the node's `NodeName` line without names and state, plus its `gres.conf` types.
- Remaining nodes are split by largest remainder in proportion to production counts, capped at each group's size. More groups than `max_nodes` is refused with the needed number.
- Sampling keeps at least one job per (account, QOS, partition) stratum so every account and QOS is present for fairshare and QOS limits; the seed is fixed.
- The dilation factor is `max(1, trace span / target)`: a short trace is not stretched. The span runs from the first submit to the last end.
- Scaled: `PriorityDecayHalfLife`, `PriorityMaxAge`, `PreemptExemptTime`, `PriorityCalcPeriod`, `OverTimeLimit`, `MinJobAge`, `KillWait`, `SchedulerTimeSlice`, `InactiveLimit`, `WaitTime`, the duration options of `SchedulerParameters` (`bf_interval`, `bf_resolution`, `bf_window`, `bf_max_time`, `sched_interval`, `batch_sched_delay`), partition `MaxTime` and `DefaultTime`, QOS `GraceTime` and `MaxWall`, job runtimes and limits. Daemon and node timeouts (`SlurmctldTimeout`, `SlurmdTimeout`, `MessageTimeout`, health check and power timers) are lab-owned: they keep the workbench's own stable values. A scaled value is never below one second (one minute for the minute-unit keys).
- The memory the governor must admit for a run is `nodes x 13 MB + 250 MB` (`lab_slurm.admission_mb`); the apply command (issue 553) passes it to `admit`.

**Implementation choices of steps 1 and 2, not decided by the owner (to confirm):**

- The run always maps users, so `--keep-users` stays an option of `get lab` only (from decision 5).
- The seed also drives the sampling; its default is 1, the seed `get lab` samples with, so a default run replays the jobs the plan showed.
- A candidate-only run takes no snapshot and has no restore or compare.
- An aborted A/B run whose snapshot was taken collects the side in progress (best effort) and restores the snapshot. (The issue's acceptance says "cluster restored after abort"; whether that means the snapshot or `remove lab` is not stated.)
- The 5 % pause limit is checked per side, against one side's length.
- The snapshot is taken before `apply_baseline` (the issue's order). **Decided (owner, round 3, 2026-11-17): keep it.** A restore covers only the accounting database and the controller's spool, not the slurm.conf overlay, the lab marker, Prometheus rules, Kubernetes objects or Teleport roles, so an aborted run's reason names `benchctl remove lab NAME`, and `remove lab` counts a row the restore already removed (`Nothing deleted`) as gone instead of refused (unit-tested; sacctmgr's exact message for a missing row and whether `sacctmgr load` reconciles or only adds are not verified live).
- A trace shorter than the target is not stretched (`time_factor` is at least 1, as in the issue 551 addendum), so its run is shorter than `target_hours`; the run records both.
- The restore needs a new start step in the slurm-ctl image (`restore-state`, run before slurmctld; it does nothing without a restore tar), because nothing can be exec'd into the controller while slurmctld is stopped.
- An account, QOS, partition or TRES value equal to a production user name makes the jobs file refuse (decision 5), rather than being renamed.

How steps 1 and 2 work:

- **States.** A/B: `idle, snapshot, apply_baseline, replay_a, collect_a, restore, apply_candidate, replay_b, collect_b, compare, report, done`; candidate only: `idle, apply_candidate, replay_b, collect_b, report, done`; `aborted` from any state that has not ended. A pause (L2) is a flag on a replay state; its time adds to `paused_s` (and to that side's own count), and a side paused for over 5 % of the run length marks the run not comparable.
- **Files.** `compose/generated/lab/NAME/reports/RUN/` holds `run.json`, `progress.json` (ADR 0049's `{name, state, percent, submitted, running, pending, paused_s}` plus the run id, side and flags, written atomically), the frozen `jobs.json` (read-only, its sha256 in `run.json`, checked before each side) and `a/`, `b/` with each side's `sacct` export. A job keeps only key, lab user, account, QOS, partition, TRES, node count, scaled submit, run and limit times, kind and exit code (OOM exits 137).
- **Pairing.** The driver names each job by its key (`j0001`), so A and B pair by key: the restore makes run B reuse run A's job ids.
- **Snapshot.** `compose stop slurmctld` (it writes its state on the way down), `docker cp` the spool out, `mariadb-dump` the accounting database, start slurmctld. The JWT key is never saved: the entrypoint installs it at every start from the keys `up` makes (issue 465).
- **Restore.** Only after run A's accounting is in the report folder (the restore erases it). Stop slurmctld and slurmdbd, drop and reload the database, dump it again and compare, start slurmdbd, `docker cp` the tar into the stopped controller, start it. The image's `restore-state` (run before slurmctld in the container's command) empties the spool except the JWT key, extracts the tar, writes the sha256 of every file and removes the tar. The run is refused (aborted) when a file or the database differs. The database compare ignores `AUTO_INCREMENT=` counters, which a reload resets.
- **Abort.** An aborted A/B run whose snapshot was taken collects the side in progress (best effort) and restores the snapshot, so the cluster is back where it started.
- **Not exercised live.** The command sequence is unit-tested against a fake Docker and the `restore-state` script runs for real in a temporary folder; `tests/real/test_lab_run_real.py` is written and not yet run.
- **A restore can be run again from any point it was cut off** (owner decision round 3, Q1): a failed database reload, a failed copy of the spool into the stopped controller, or a controller that never reports its sums. Each step is idempotent (stop a stopped service, drop and reload the database, copy the tar again; `restore-state` removes the tar last), so a second `restore` reproduces the snapshot. Three unit tests, one per cut-off point.

**Steps 3 to 5 (driver, governor verbs, CLI), built 2026-11-17, not run live:**

- **Driver** (`images/slurm-ctl/lab_driver.py`, decision 1). An unlabelled one-shot container of the slurm-ctl image (`docker run --rm`, `--memory 250m`, no `workbench.class` label, every mount read-only: the jobs file, slurm.conf, the munge key, the flags directory, the script itself, mounted from the checkout so a change needs no image rebuild). It starts munged, creates the run's `lab-uNNN` users inside itself (uid 30000 + N, derived from the name), and submits each job at its lab time as `runuser -u lab-uNNN -- sbatch --job-name=KEY --chdir=/tmp --output=/dev/null ... --wrap "sleep S; exit C"` (a timeout sleeps its limit, in whole minutes, plus 60 s; OOM exits 137; CPUs, memory and GRES per node from the TRES; account, QOS and partition when they are plain names). A refused submission is counted (`rejected`) and the replay goes on. The replay clock stops while `flags/lab.paused` exists; `flags/lab.abort` cancels its jobs and ends it; `arrivals.paused` (L1) is never read. It prints `@progress` and `@done` JSON lines; the host writes the run's files, so nothing in a bind mount becomes root-owned. Its own deadline is twice the run length plus an hour.
- **Governor** (`governor/labrun.py`, decision 2). `lab-run` (name, optional `ab`, `target_hours` 0.5 to 6, `seed`): refused at L2 and up, while another run or a change runs; a short `benchctl run lab NAME --prepare` child freezes the jobs and prints the lab node count, the governor admits `nodes x 13 + 250` MB itself (a refused run's folder is removed), then starts the run's child `benchctl run lab NAME --run RID --execute` and a supervising thread. The thread only maps the level to flags once a second: `lab.paused` at L2 and up (removed below L2), `lab.abort` at L3 and up ("aborted under memory pressure (L3)"). `lab-stop` writes the abort flag at any level. While a run is active, `scale`, `set-profile`, `apply-plan`, `lab-apply`, `lab-restore` and `lab-validate` are refused with one message naming `benchctl stop lab NAME`. A governor that restarts finds `compose/generated/lab/run-active.json` and recovers the run (see round 3 below). `status` carries the run's progress in `lab` (`state`, `percent`, `submitted`, `running`, `pending`, `paused_s`, `run`, `replay_side`, `paused`, `comparable`, `reason`, `restore_pending`); without a run the block is the marker's, as before. `lab-apply` now asks admission (`nodes x 13 + 250` MB, the node count from `benchctl get lab NAME -o json`).
- **The run's child** (`benchctl/lab_steps.py`) walks `lab_run.drive` with the real steps (apply through `lab_apply.apply`, the driver, collect, snapshot, restore, `compare.json`, a short `report.json`; the report and verdict are issue 555). It reads the abort flag before every state, and while the pause flag exists (L2 and up) it waits before the next state, because snapshot, apply, collect and the restore fork Docker (GV-8); a state already running finishes, as a `_change` does. That wait is not counted in `paused_s`, which measures the replay only. After an abort it waits until the governor says L0 or L1 before the restore (GV-8: the restore forks Docker and reloads MariaDB), showing `restore_pending`; if the governor does not answer for 5 minutes the restore is not run and the snapshot is kept.
- **Decision 9, the `lab_run` label.** While a side replays the child writes `compose/generated/prometheus/lab-run/slurm.json`: slurmctld's four metrics paths with a hidden `__lab_run` label (`NAME/RUN/SIDE`). The static `lab-run` job in `observability/prometheus.yml` keeps only targets carrying it and copies it to `lab_run`. Prometheus re-reads file_sd files by itself, so nothing is rewritten or reloaded per run; a running stack needs one Prometheus reload (or `benchctl up`) to learn the job. Only these series carry the label: sim-nodes, the GPU exporter and the governor's metrics do not. The file is written by the host side of the replay, not inside the container, so it is not root-owned.
- **CLI.** `benchctl run lab NAME [--ab] [--target-hours H] [--seed S]` returns once the governor has started the run or refused it (round 3, Q5); `benchctl status` shows its progress; `benchctl stop lab NAME` ends it. Bare `benchctl stop` still stops the web page, the cluster and the governor.
- **`sacct -u` with users unknown on the node (item 7 of the PR 865 decisions, checked by reading the source, not live).** Slurm 26.05.5 (tag `slurm-26-05-5-1`): `sacct -u` calls `slurm_addto_id_char_list`, whose `_convert_to_id` turns each name into a uid with `uid_from_string` on the host where sacct runs (`src/sacct/options.c`, `src/common/slurm_protocol_defs.c`, `src/common/uid.c`). An unknown name is `Invalid user id: NAME`, the list is emptied and sacct exits 1; a number with no passwd entry is refused the same way (`ESLURM_USER_ID_UNKNOWN`). So `sacct -u lab-u001,...` fails on slurmctld until those users exist there. The collect now runs `sacct -a` and keeps the rows of the lab users or the run's job keys.

**Owner decisions, round 3 (2026-11-17, after the PR 866 review; issue 554), and how they are built:**

- **Item 4: the snapshot stays before the baseline.** A restore covers only the accounting database and the controller's spool; the slurm.conf overlay, the lab marker, Prometheus rules, Kubernetes objects and Teleport roles stay. So an aborted run that had applied a side ends its reason with "`benchctl remove lab NAME` returns to the plain cluster", and `remove lab` counts a row the restore already removed (sacctmgr's `Nothing deleted`) as gone. Not verified live: that message, and whether `sacctmgr load` reconciles or only adds.
- **Q1: the run-scoped child stays; no new daemon.** SPEC C-24 now reads: work one command starts and that ends with it is allowed (one-shot containers, a supervising thread, a run-scoped child the governor starts, tracks by pid and waits for). systemd's default `KillMode` (control-group) is kept, so stopping the root service also ends the child (`process` and `none` are discouraged by systemd, `systemd.kill(5)`). `run-active.json` records the child's pid and its start time (field 22 of `/proc/PID/stat`, so a reused pid is not mistaken for it). At start the governor's `recover()` keeps the phase `recovering` (the same refusals as a run) until the old run is done, or aborted with no restore owed: a live old child is asked to abort and restores itself; if it is gone, a restore-only child (`benchctl run lab NAME --run RID --recover`) removes the run's driver containers by name, ends the run as aborted (collecting the side in progress) and restores the snapshot once the level is at L0-L1. The restore is re-runnable from every cut-off point (three unit tests).
- **Q2: the `lab-uNNN` user mapping is issue 869**, not this one (dump users plus trace users, numbered once, append-only; a trace user without an account counts as "rejected: no association").
- **Q3: refusals.** While a run is `preparing` (a placeholder set at the top of `lab-run`, so two requests cannot both start), `running` or `recovering`: `scale`, `set-profile`, `apply-plan`, `admit` (so `benchctl up`), `lab-apply`, `lab-restore`, `lab-validate`, `slurm-step remove-jobs` and `import lab --replace` are refused with one message; `freeze`, `thaw`, `stop`, `start` and `node-state` stay allowed (operator relief). `benchctl down` and a bare `benchctl stop` refuse (exit 3; `scripts/benchctl-launch stop` runs `down` first, so nothing is stopped) and name the two ways out: `benchctl stop lab NAME`, wait, then `down`; or `--force`, which sends `lab-stop` with `force` (the governor's `lab.norestore` flag): the run aborts, skips the restore, keeps the snapshot and names `remove lab`. `--yes` never overrides; with `BENCHCTL_AGENT=1` `--force` also needs `--yes`. A node action during a replay (the governor's `node-state`, `freeze`/`thaw`/`stop`/`start` of a node container, `netem-set`, `submit-job`, `slurm-step`; and every step the scenario engine applies, `benchctl/lab_interference.py`) is allowed and appended to the run's `interference.jsonl`; the run is then not comparable and `progress` names the first action and its time.
- **Q4: kept.** The restore after an L3 abort waits for L0-L1, with no time limit while the level stays high (`restore_pending` in status). (If the governor stops answering for 5 minutes, the child keeps the snapshot and says `remove lab`.)
- **Q5: `lab-run` answers at once** (`started`, state `preparing`, the pattern of `apply-plan`, W-13). A thread prepares and admits; `status.lab` shows `preparing`, `refused` (with the reason, kept until the next start) or the run's state. `benchctl run lab` watches `status` and prints one line for either outcome. The `reader` docstring says it also runs `--prepare`, which writes only the new run's own folder.

Still open: the live checks (all `tests/real` tests are written, none run), the monitoring client, and the lab nodes (issue 863) and users (issue 869) without which a real trace cannot be replayed end to end.

**Addendum, issue 555 (alerts and repeats, 2026-11-18).** `lab_prom.py` reads only the built-in `ALERTS` series from Prometheus over each side's replay window (from the run's state history): which alerts fired, the production-equivalent time to the first one, and flaps (fired again after a gap of more than two scrape steps). No metric name is guessed; scheduler load, Kubernetes counts, idle-but-free GPUs, pending reasons and fairshare usage stay in `not_measured` until their series are checked on a live stack. Alerts are information and never change the verdict. A report counts the earlier runs of the same frozen jobs (`jobs_sha256`): one run is labelled single-run, two or more show whether their verdicts agree (`repeat`). The report also has a wait-by-QOS table. Contract 2.5.

**Addendum, issue 555 (repeat loop, 2026-11-18).** `run lab --repeat N` (1 to 10) starts the same run N times one after the other (same seed, so the same frozen jobs) and waits for each run's own record to be done before the next; an aborted run stops the loop.

**Addendum, issue 555 (pending reasons and scheduler load, 2026-11-20).** Two more metrics, both defined by the Slurm tools themselves, so nothing is guessed:
- Pending-reason mix: the collect adds sacct's `Reason` field. sacct(1) (Slurm 26.05.5) defines it as "the last reason a job was blocked from running for something other than Priority or Resources", saved even if the job ran (`print.c` prints `state_reason_prev`); the mix counts each reason, and the jobs with `None` are shown as "only Priority or Resources". The catalogue's "QOS limit dominating pending" suggestion fires when more than half of the candidate's jobs with a reason name a QOS limit (the reason strings that start with `QOS`).
- Scheduler load: the `lab_run` series of decision 9, gauges only (`slurm_schedule_cycle_last`, `slurm_bf_cycle_last`, `slurm_schedule_queue_len`, `slurm_bf_queue_len`, `slurm_server_thread_cnt`, `slurm_agent_queue_size`, `slurm_slurmdbd_queue_size`, names from Slurm 26.05.5's `metrics/openmetrics` plugin), max and median of the samples over the side's replay. The `*_max`, `*_mean` and `*_cnt` values count from slurmctld's last start or sdiag reset, which can precede the side, so they are not read. Cycle times are real microseconds and never time-scaled; information only, never the verdict. `tests/real/test_slurm_metrics_real.py` checks the names on the live controller (passed 2026-11-20; a real lab run has not read them yet).
- The catalogue's "alert flapping" suggestion fires when an alert flapped on the candidate side.
- Still not built, as each needs an owner decision: idle-but-free GPUs (which definition), fairshare usage spread (a new `sshare` step at the end of each side, and which column), Kubernetes claim, quota and 429 counts (the replay submits Slurm jobs only, so they would always be zero), and the median and range across repeats promised above (only verdict agreement is built). The `lab-idle` and `lab-run` memory measurements need a live lab run.

**Addendum, issue 554 (`run lab --scenario S`, owner approval of 2026-11-20).** A scenario attached to the run itself, so both sides meet the same faults at the same lab times (the "same faults" bullet of the decision). Design note: what was adopted from how simulation, replay and chaos tools handle faults during paired or deterministic runs, and what was rejected.

Sources read (primary pages): FoundationDB's simulation and testing page (apple.github.io/foundationdb/testing.html), TigerBeetle's VOPR notes (docs/internals/vopr.md in the tigerbeetle repository), SimPy's real-time simulation guide (simpy.readthedocs.io, topical guide "Real-time simulations"), Jepsen's combined nemesis package (jepsen/src/jepsen/nemesis/combined.clj), Chaos Mesh's "Run a Chaos Experiment" and "Define Scheduling Rules" pages (chaos-mesh.org/docs), the Principles of Chaos Engineering (principlesofchaos.org) and LitmusChaos's probes page (docs.litmuschaos.io/docs/concepts/probes).

Adopted:
- **One clock for jobs and faults** (FoundationDB: the simulation "steps through time, synchronized across the system"; SimPy: a single factor from simulated time to wall time). A scenario's `at:` is production time and plays at `at / factor` seconds of the side's replay clock (`--speed` = the run's time factor; sim.yaml `time_dilation` is not applied again). The player's clock follows the driver's `replay_s` (`@progress`) and runs on the host's monotonic clock between two lines, so both sides see each step at the same lab time.
- **Determinism, not a seed** (FoundationDB: determinism "allows perfect repeatability"; VOPR: deterministic from a seed and the commit). Our engine has no random input to seed, so the seed changes nothing in it; the schedule is fixed by freezing the resolved scenario into the run folder (`scenario.json`, read-only, its sha256 in `run.json`, checked before each side), as the jobs are. No fake seeding was added.
- **Heal after each phase** (Jepsen's nemesis packages return a final generator "to clean up any failure modes at the end of a test"). At the end of each side, before its collect and so before the A to B restore, and after an abort once the level is at L0-L1, the run undoes what the scenario can leave: containers it powered off are unpaused, slurmd's hold file is removed where it stopped slurmd, and every node it named is resumed. The snapshot restore does not unpause a container, so this is needed even between A and B. A restore-only child after a governor restart heals too. `benchctl down --force` skips it (the cluster goes down anyway).
- **The scenario is part of the environment held constant, not a difference** (Principles of Chaos: compare a control and an experimental group under the same conditions). The run's own steps are written to `interference.jsonl` with `by: lab-run` and `Run.comparable()` skips them; any other fault or scenario during a replay still marks the run not comparable.
- **Fail closed at prepare.** A scenario that cannot play identically on both sides is refused before admission, one message per problem: a target other than `slurm` (the BMC farm, BCM, GPU exporter, DCGM, fault model and switch know only sim.yaml's nodes, the hardware inventory has no lab nodes), `submit`, `cancel` and Slurm's power save (`power_down`, `power_up`, `reboot`, which go through the BMC), an expectation other than `slurm.node_state`, `slurm.job_state` and `slurm.stepd`, a node that is not a lab node, a scenario that ends after the side, and two steps on one node that the factor puts under one second apart (the one-second floor of the time scaling; the message names the factor and the smallest scenario gap that fits). Node selectors pick lab nodes: `cpu` without GPUs, `gpu` with, in the downscale's order. Steps through Slurm keep the Slurm (production) name; steps on the container use `lab-node-NNN`; the report names every node by its Slurm name, so `export lab-report --anonymize` maps all of them.
- **No new process.** The player is a thread of the run's child (the child already exists); it applies steps with the host CLI's Docker access, as `benchctl scenario run` does. The page cannot attach a scenario (W-17l unchanged).

Rejected:
- **Chaos Mesh's pause semantics.** Chaos Mesh starts "recovering the injected fault" when an experiment is paused and keeps counting paused time toward its deadline. Here an L2 pause keeps injected faults in place and stops the scenario clock (no step is applied and no expectation polled while paused, GV-8), so the remaining steps move later by exactly the pause on that side. Recovering on pause would give the two sides different fault exposure; the pause itself is already measured (over 5 % of a side marks the run not comparable).
- **Expectations as the verdict** (LitmusChaos: probes are "the logical conjunction" of a fault's pass criteria). The verdict compares the configuration; the scenario's expectations are reported per side (`scenario_expects`, with a `differs` flag) and never change it. Their `within` windows are scaled by the factor like the steps, while daemon timeouts are lab-owned and not scaled, so an expectation about Slurm noticing a dead node can fail at a high factor; that is information, not a defect of the candidate.
- **Random or rotating fault schedules** (Jepsen's staggered nemesis, VOPR's seed-chosen faults, FoundationDB's swizzle-clogging). They find bugs by variety; an A/B comparison needs the opposite, the same schedule twice.
- **Resolving selectors against sim.yaml's nodes.** Faults on simulated nodes would not touch the replayed jobs (they run only on lab nodes).

Built: `benchctl/lab_scenario.py` (freeze, checks, heal, the player), the `pools` argument of `benchctl/selectors.py`, `by` in `scenario.execute` and `scenario.run`, the governor's checked `scenario` field on `lab-run` (`governor/control.py`, `governor/labrun.py`), `--scenario` on `benchctl run lab`, the report's scenario section, and the scenario `lab-node-loss` (SC-59). Unit tests: `tests/test_lab_scenario.py`. **Not run live:** `tests/real/test_lab_scenario_real.py` (lab nodes, a drain through slurmctld, a paused container, the clock held by the pause flag, the heal) is written and not run; no whole A/B run with a scenario has run; not tested against the monitoring client.
